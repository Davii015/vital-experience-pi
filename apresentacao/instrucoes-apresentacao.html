2. Resumo rápido do projeto

O Vital Experience é um sistema web de monitoramento físico e sensorial voltado para reabilitação, fisioterapia e esporte adaptado. Ele integra sensores vestíveis — como monitores cardíacos, acelerômetros, oxímetros e eletromiógrafos — com uma plataforma que permite a profissionais de saúde e educação física acompanhar em tempo real o estado físico de seus pacientes e atletas.

O sistema oferece cadastro de profissionais, usuários monitorados, dispositivos sensores e sessões de atividade, além de visualização de dados fisiológicos (frequência cardíaca, SpO₂, nível de esforço, fadiga) e geração de relatórios de evolução individualizados.

Stack tecnológica

  • Frontend: HTML5 + CSS3 + JavaScript puro — 9 telas completas e responsivas
  • Backend: Node.js + Express — API REST com autenticação JWT
  • ORM: Prisma 5 — schema centralizado com migrations versionadas
  • Banco de dados: Supabase PostgreSQL — cloud, com suporte a pgBouncer
  • Dados simulados: localStorage (frontend autossuficiente para demonstração)

6. Perguntas prováveis da banca
Por que escolheram esse problema?
Identificamos que profissionais de fisioterapia e educação física não possuem ferramentas acessíveis para monitorar objetivamente o estado físico de pacientes durante as sessões. A maioria dos sistemas existentes é cara, fechada ou não integra múltiplos sensores. O Vital Experience propõe uma solução web open-source, modular e adaptável ao contexto brasileiro.
Como os sensores funcionariam na prática?
Na versão atual, os dados são simulados via software para demonstração. Na integração real, os sensores vestíveis enviariam dados via Bluetooth ou Wi-Fi para um gateway (aplicativo mobile ou dispositivo IoT), que faria requisições POST para nossa API REST em /api/sensor-data. O Prisma registraria cada leitura vinculada à sessão ativa do paciente.
O sistema já coleta dados reais?
O frontend opera com dados simulados via localStorage para garantir demonstração autônoma. O backend e o banco Supabase estão configurados e funcionais — o banco possui dados reais inseridos via seed do Prisma. A integração completa frontend–backend é o próximo passo previsto.
Por que PostgreSQL/Supabase?
PostgreSQL é um banco relacional robusto, adequado para dados estruturados com múltiplos relacionamentos como os do nosso domínio. Escolhemos Supabase por ser uma plataforma cloud gratuita para projetos acadêmicos, com suporte a connection pooling via pgBouncer — essencial para ambientes serverless e alta concorrência.
Por que usar Prisma?
Prisma elimina SQL manual propenso a erros, oferece type-safety, migrations versionadas e Prisma Studio para visualização dos dados. O schema declarativo em schema.prisma é a fonte única de verdade da estrutura do banco — qualquer mudança é rastreável no histórico do Git.
Como garantem a segurança dos dados?
Utilizamos JWT para autenticação stateless, bcrypt para hash de senhas, variáveis de ambiente para todas as credenciais sensíveis (nunca no código), e o arquivo .env real está no .gitignore — apenas o .env.example com placeholders vai ao GitHub. Os dados biométricos dos pacientes são tratados conforme os princípios da LGPD.
Como os profissionais acessam os dados dos usuários?
O sistema associa cada usuário monitorado a um profissional responsável. As sessões e leituras de sensores estão vinculadas a essa relação. Na tela de Relatórios, qualquer operador autenticado pode visualizar o histórico completo por paciente — incluindo evolução de FC, esforço e fadiga ao longo das sessões.
Qual foi a evolução após a segunda entrega?
Incorporamos o ORM Prisma com schema completo de 6 modelos e 4 enums, configuramos o Supabase PostgreSQL com connection pooling, implementamos migrations versionadas, criamos seed de dados fictícios realistas, adicionamos documentação técnica completa (API, diagramas, segurança, apresentação) e subimos o projeto ao GitHub com proteção das credenciais.
O que ainda falta para o projeto ficar completo?
Integração real do frontend com o backend (substituir localStorage pela API REST), deploy em nuvem (Railway ou Render para o backend), WebSocket para monitoramento em tempo real, integração com SDKs de sensores físicos e implementação de log de auditoria de acesso.
Como cada integrante contribuiu?
Davi (PO): definição de requisitos, validação de entregas, demonstração do frontend e identidade visual. Hugo (SM): estrutura do backend, rotas, autenticação e facilitação do Scrum. Jorge (Dev): modelagem do banco, Prisma, arquitetura e diagramas. Luísa (QA/Docs): requisitos, regras de negócio, segurança, privacidade e documentação completa.
O que acontece se o banco não conectar durante a apresentação?
O frontend funciona de forma completamente autônoma via localStorage — ele não depende de backend ativo. Todos os CRUDs, gráficos, relatórios e simulação de sensores funcionam sem conexão ao banco. Isso garante que a demonstração visual do sistema nunca seja comprometida.

9. Plano B — contingências técnicas
⚠ Backend não roda

Use apenas o frontend com localStorage. Todos os CRUDs, gráficos e relatórios funcionam sem backend. Mencione que o backend foi testado e está funcional, e explique a arquitetura de forma verbal.

⚠ Banco Supabase não conecta

O frontend não depende do banco. Mostre o schema.prisma, o arquivo de migration e o seed.js para comprovar a estrutura. Se tiver acesso ao Supabase Dashboard pelo celular, mostre as tabelas pela interface web do Supabase.

⚠ Internet cai durante a apresentação

O frontend funciona 100% offline via localStorage. O Supabase não estará disponível, mas toda a demonstração visual continua normalmente. Tenha prints das telas do banco como backup.

⚠ GitHub não abre

Mostre o repositório local — o código está na máquina. Abra o VS Code com a estrutura de pastas visível na sidebar. Explique verbalmente a organização e navegue pelos arquivos principais.

⚠ Alguma tela do frontend dá erro

Abra o console do navegador (F12) rapidamente para identificar o problema. Se não resolver em 30 segundos, recarregue a página. Se persistir, pule para a próxima tela e retorne ao final. O sistema tem 9 telas — a apresentação não depende de uma tela específica.

⚠ Prisma Studio não abre

Use o Supabase Dashboard (supabase.com → seu projeto → Table Editor) para mostrar os dados diretamente na interface web. O visual é igualmente profissional e dispensa o Prisma Studio.
