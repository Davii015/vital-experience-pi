22.1 Frontend

O frontend do Vital Experience permanece implementado em HTML5, CSS3 e JavaScript, com páginas específicas para autenticação, dashboard, usuários monitorados, profissionais, sensores, sessões, dados de sensores, relatórios e perfil do administrador. Na Fase 02 do 6º período, a principal evolução foi substituir a camada de demonstração baseada em armazenamento local por um cliente HTTP centralizado em frontend/js/api.js. As páginas continuam organizadas em frontend/pages, os comportamentos de cada tela ficam em frontend/js e o servidor Express disponibiliza os arquivos estáticos em /app.

O cliente utiliza fetch e corpos JSON para comunicar-se com os endpoints /api. A URL-base padrão é /api, na mesma origem da interface; a variável opcional window.VE_API_BASE_URL permite apontar para outro endereço quando a implantação justificar essa separação. A camada api.js traduz os nomes de campos e os valores enumerados do backend para os rótulos apresentados na interface. Após operações de criação, atualização ou exclusão, a coleção correspondente é novamente consultada para que a tela reflita a resposta do servidor. Falhas de conexão e respostas HTTP não bem-sucedidas são convertidas em mensagens de erro apresentadas ao operador.

O login da interface envia POST /api/auth/login com e-mail e senha de um administrador cadastrado. A API define um cookie de sessão HttpOnly e devolve um token de proteção contra requisições forjadas, utilizado automaticamente pelo cliente nas operações que modificam dados. Ao carregar uma página protegida, o frontend consulta GET /api/auth/me para verificar a sessão; não armazena o JWT em localStorage. A tela de perfil utiliza GET e PUT /api/auth/me, PUT /api/auth/password e POST /api/auth/logout. A troca de senha exige nova autenticação.

As telas de usuários, profissionais, sensores e sessões consomem os endpoints de consulta e manutenção dos respectivos recursos. O formulário de usuário informa a data de nascimento, enquanto a idade exibida é calculada pela interface. A tela de leituras consulta /api/sensor-data e permite registrar uma leitura sintética de demonstração por POST /api/sensor-data em uma sessão em andamento; esse recurso não equivale à aquisição de dados de um dispositivo físico. O dashboard utiliza /api/reports/summary, além das listagens necessárias aos indicadores e sessões recentes. A tela de relatórios utiliza /api/reports/user/:userId para apresentar a consolidação calculada no backend.

O frontend inclui filtros, estados vazios e atualização das tabelas após as operações suportadas. Dados textuais recebidos da API são escapados antes de sua inserção em trechos HTML dinâmicos. Os alertas automáticos foram identificados como pendência na própria interface, pois ainda não há fonte persistente para esse recurso. A integração foi exercitada por teste HTTP local que executou o cliente api.js, mas o percurso visual completo de todas as telas em navegador real e a persistência em PostgreSQL continuam pendentes de validação em ambiente configurado.

22.2 Backend

O backend do Vital Experience é uma API REST em Node.js e Express, estruturada em routes, controllers, services, middlewares, utils, errors e config. O servidor interpreta JSON, publica o frontend estático em /app, atende a API em /api e mantém os endpoints públicos / e /health. Os sete grupos de rotas da API são auth, users, professionals, sensors, sessions, sensor-data e reports. As routes definem método e caminho e aplicam autenticação; os controllers adaptam parâmetros e respostas HTTP; os services concentram validação, regras de negócio e operações de dados; e o middleware de erros padroniza as falhas.

A autenticação consulta o administrador persistido, compara a senha ao hash bcrypt e emite JWT com validade padrão de uma hora. Para o navegador, POST /api/auth/login devolve perfil e token CSRF e define o JWT em cookie HttpOnly, SameSite=Strict e Secure em produção. Em requisições autenticadas por cookie que alterem dados, o middleware exige X-CSRF-Token. Para clientes não navegadores, o login aceita o modo bearer e devolve token para uso em Authorization: Bearer. A cada requisição protegida, o middleware valida assinatura, expiração, papel ADMIN e tokenVersion do administrador no banco. GET /api/auth/me consulta o perfil; PUT /api/auth/me atualiza nome ou e-mail; PUT /api/auth/password verifica a senha atual, exige nova senha de no mínimo 12 caracteres e incrementa tokenVersion, revogando tokens anteriores; POST /api/auth/logout remove o cookie local. O logout isolado não revoga imediatamente um Bearer ainda válido. Existe apenas o papel ADMIN, sem isolamento de dados por profissional ou paciente.

Os endpoints GET e POST /api/users, /api/professionals, /api/sensors e /api/sessions, acompanhados de GET, PUT e DELETE por identificador, implementam as operações de manutenção dessas entidades. GET e POST /api/sensor-data, GET /api/sensor-data/session/:sessionId e DELETE /api/sensor-data/:id permitem registrar e consultar leituras. GET /api/reports/summary devolve totais globais e GET /api/reports/user/:userId consolida sessões, leituras e relatórios existentes do usuário, com média de frequência cardíaca e distribuições de esforço e fadiga. Essa consulta não gera automaticamente um novo registro clínico de Report.

As regras de negócio exigem campos obrigatórios e vínculos válidos; verificam situação ativa de profissionais, usuários e sensores quando aplicável; impedem a remoção de profissional com usuários ativos; exigem horário final coerente para sessão finalizada; rejeitam leitura em sessão cancelada; e conferem se o sensor informado está ativo e pertence ao usuário da sessão. As entradas de frequência cardíaca, movimento, saturação, temperatura, passos, bateria, datas e valores enumerados são validadas nos services. Esforço e risco de fadiga são recebidos como classificação da leitura; o backend ainda não implementa um algoritmo clínico que os derive automaticamente. A interface de demonstração produz uma leitura sintética manual, identificada como tal.

O acesso a dados é implementado por instância compartilhada do Prisma Client, de acordo com o schema e as migrations do repositório. O modelo contém Admin, Professional, User, Sensor, Session, SensorData e Report. Na Fase 02, Admin recebeu tokenVersion, com migração versionada e atualização da referência SQL. O seed de demonstração foi protegido: é proibido em produção, exige confirmação literal para limpar as tabelas e senha própria de pelo menos 12 caracteres. Erros conhecidos retornam, conforme o caso, HTTP 400, 401, 403, 404 ou 409; falhas inesperadas retornam 500 sem detalhes internos ao cliente.

Foram executados geração do Prisma Client, validação do schema e verificação de sintaxe. Dois testes automatizados passaram: disponibilidade de /health e integração HTTP local envolvendo autenticação, cookie, CSRF, CRUD de usuário, sessão, leitura sintética, agregação de relatório, edição de perfil, troca de senha, revogação de token, Bearer e rejeição de valor fisiológico inválido. O teste integrado substitui os delegates Prisma por armazenamento em memória; por isso não comprova a gravação efetiva em PostgreSQL/Supabase. A aplicação das migrations e os testes de persistência real exigem um banco de teste ainda não disponível neste ambiente.

22.3 Integração entre as camadas

A integração entre interface e backend ocorre por HTTP e JSON. O mesmo servidor Express disponibiliza, por padrão, os arquivos do frontend em /app e os recursos REST em /api, evitando dependência de origens distintas no ambiente local. Cada página consulta /api/auth/me para identificar o administrador; frontend/js/api.js centraliza fetch, credenciais do navegador, serialização dos corpos, leitura das respostas, tratamento de erros e adaptação dos campos exibidos. As operações autenticadas por cookie que alteram dados incluem X-CSRF-Token. Quando a resposta é 401 para uma sessão protegida, o cliente limpa seu estado em memória e encaminha o operador para o login. A troca de senha orienta nova autenticação.

O fluxo de cadastro exemplifica a integração: o administrador autentica-se por POST /api/auth/login; o navegador recebe cookie HttpOnly e token CSRF; a tela envia POST /api/users com JSON, cookie e cabeçalho CSRF; a rota protegida chama controller e usersService; o service valida os dados e usa Prisma Client; a resposta HTTP 201 é recebida pelo cliente, que atualiza a lista por GET /api/users. De modo semelhante, a criação de uma sessão e o envio de uma leitura sintética de demonstração utilizam POST /api/sessions e POST /api/sensor-data. O relatório de usuário é consultado por GET /api/reports/user/:userId e o dashboard obtém totais por GET /api/reports/summary.

O teste automatizado executou o servidor HTTP local e o código real do cliente frontend, comprovando métodos, caminhos, cabeçalhos, corpos JSON, autenticação, proteção CSRF, respostas e atualização do estado para os fluxos citados. Os delegates do Prisma foram substituídos por objetos em memória para permitir o teste sem serviço externo. Assim, há evidência de integração HTTP entre frontend e backend, mas não de persistência real em PostgreSQL/Supabase; esta última deverá ser verificada após configurar um banco de teste, aplicar as migrations e repetir operações de criação, consulta, alteração e exclusão. Também permanecem pendentes a validação visual completa em navegador real, o uso de sensores físicos, os alertas automáticos e a autorização por profissional ou paciente.

20 ARQUITETURA GERAL DO SISTEMA

O Vital Experience mantém a separação entre interface web, API REST e persistência relacional. A interface HTML5/CSS3/JavaScript é servida pelo Express em /app e chama /api por meio de frontend/js/api.js. O backend está organizado em routes e middlewares, controllers, services e acesso a dados com Prisma Client. As routes definem o contrato HTTP e a proteção de acesso; os controllers concentram a adaptação da requisição e da resposta; os services aplicam regras de negócio e executam consultas; o Prisma mapeia as sete entidades e suas relações para PostgreSQL. As URLs do banco são fornecidas pelo ambiente, sem credenciais no repositório.

O fluxo principal é: administrador no navegador → cliente HTTP do frontend → rota Express protegida por autenticação e, quando aplicável, CSRF → controller → service → Prisma Client → PostgreSQL. A resposta retorna em JSON e é convertida para os rótulos e estados das telas. O uso da mesma origem para frontend e API simplifica a sessão por cookie. Existe suporte opcional a uma origem de frontend explicitamente configurada para CORS, mas a política de cookies entre origens distintas requer avaliação própria na implantação. Os serviços de autenticação consultam Admin e tokenVersion a cada requisição protegida. O tratamento de erros HTTP é centralizado.

O esquema Prisma e suas migrations são a fonte de referência da estrutura persistente. O arquivo database/schema.sql é uma referência legível alinhada ao esquema; não substitui as migrations. A arquitetura está implementada no código, mas a conexão a um PostgreSQL/Supabase real não foi testada nesta execução. Não fazem parte da arquitetura atual sensores físicos conectados, WebSocket, processamento em tempo real contínuo ou motor persistente de alertas.

5 SITUAÇÃO ATUAL DO PROJETO

O Vital Experience encontra-se na Fase 02 do 6º período. A Fase 01 consolidou a organização do backend em rotas, controllers, services, middlewares e Prisma Client. Não havia banco de teste disponível nesta execução; o seed destrutivo não foi utilizado.

TEXTO FINAL PARA COPIAR E COLAR:
19.1 Escolhas Tecnológicas
O frontend utiliza HTML5, CSS3 e JavaScript e comunica-se com a API por fetch. O backend utiliza Node.js e Express; Prisma Client organiza o acesso programado ao PostgreSQL/Supabase. A interface e a API são servidas, por padrão, na mesma origem. A autenticação do navegador emprega cookie HttpOnly com proteção CSRF; clientes de API podem usar Bearer. localStorage não constitui mais a fonte de registros do sistema.
19.2 Experimentação Técnica e Primeiros Testes
A verificação técnica incluiu geração do Prisma Client, validação do schema, checagem de sintaxe dos arquivos JavaScript e dois testes automatizados aprovados. O teste integrado executou requisições HTTP reais entre o cliente frontend e a API local, abrangendo autenticação, CRUD de usuário, sessão, leitura sintética e agregação de relatório. Os delegates Prisma foram substituídos por objetos em memória; portanto, o ensaio não comprova persistência em PostgreSQL/Supabase. A verificação com banco de teste e o percurso visual completo das telas permanecem atividades futuras.
